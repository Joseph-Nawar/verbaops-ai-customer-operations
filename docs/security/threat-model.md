# VerbaOps AI Phase 0 Threat Model

**Prompt-based safety is defense-in-depth, not the security boundary.** The security boundary is trusted server-side identity and tenant context, deterministic authorization and policy, typed tools, authenticated Commerce Sandbox/API access, confirmation or human approval, result verification, and auditability.

| ID | Threat | Asset | Attack scenario | Preventive controls | Detection | Verification/test | Residual risk |
|---|---|---|---|---|---|---|---|
| T-01 | Direct prompt injection | Policy, tools, and conversation data | A user tells the model to ignore safety rules and issue a refund or reveal another customer's data. | Treat the LLM as untrusted; typed tools; deterministic policy; trusted identity outside the prompt; confirmation/HITL. | Tool/policy denials, unusual instruction patterns, audit events. | Adversarial conversation suite; assert no unauthorized tool call. | Model may still produce misleading text; bounded by server controls. |
| T-02 | Indirect/RAG injection | Retrieval pipeline and user response | A knowledge document contains instructions addressed to the model to bypass policy or exfiltrate data. | Treat retrieved text as evidence only; isolate instructions from evidence; citations; policy checks outside retrieval. | Document scanning, suspicious-content flags, citation and claim review. | Poisoned-document retrieval tests; assert instructions never alter authorization. | Malicious content can reduce answer quality until quarantined. |
| T-03 | Cross-customer access | Customer, order, shipment, refund, return, and ticket data | A caller supplies another order number or persuades the model to infer a different customer identity. | Trusted customer mapping; deterministic resource authorization; tenant/customer scoping in every tool. | Denied access events and cross-scope query alerts. | Matrix tests across customers and resources. | Correct authorization depends on Commerce API enforcement too. |
| T-04 | Cross-tenant access | Tenant data and configuration | A tenant identifier in user text or model output attempts to switch the active tenant. | Server-derived tenant context; tenant-scoped queries and tools; model cannot set tenant. | Scope-mismatch logs and invariant alerts. | Multi-tenant isolation tests with forged identifiers. | Shared infrastructure misconfiguration remains possible. |
| T-05 | Hallucinated tool arguments | Commerce state and customer actions | The model invents an order, amount, item, delivery slot, or reason. | Strict input/output schemas; resource lookup; policy validation; confirmation of material values. | Schema failures, unknown-resource errors, argument-quality metrics. | Field-level argument evaluation and malformed-input tests. | A well-formed but wrong proposal can still require user correction. |
| T-06 | Duplicate/replayed writes | Orders, returns, tickets, and delivery changes | Network retry or replay repeats a cancellation, return, reschedule, or ticket creation. | Idempotency keys; safe retry semantics; immutable proposal/confirmation binding; reconciliation reads. | Duplicate-key events, replay detection, outcome reconciliation. | Replay and timeout-after-commit tests. | External API idempotency guarantees may vary. |
| T-07 | Unsafe financial actions | Refunds, credits, and financial policy | A model or caller attempts an autonomous high-value refund or discount. | Real payments and autonomous discounts/credits out of V1; high-value refunds require supervisor approval; deterministic thresholds. | Approval/audit review and denied-action metrics. | Zero-violation financial-action suite. | Human approver can still make an incorrect decision. |
| T-08 | Privilege escalation | Roles, approvals, and administration | A customer or agent claims to be a supervisor or tenant administrator. | Authenticated role claims from server context; server-side authorization; no role inference from text. | Role/scope mismatch events. | Role-confusion and forged-claim tests. | Identity-provider compromise is outside this boundary. |
| T-09 | Approval replay/spoofing | Approval requests and high-risk writes | An old approval is reused for a different amount, target, tenant, or action. | Bind approval to immutable proposal hash, target, tenant, approver, expiry, and idempotency key; recheck at execution. | Invalid signature/hash, expiry, and mismatch events. | Mutated-proposal and replay tests. | Approval UI or credential compromise remains possible. |
| T-10 | PII leakage | Customer data, logs, prompts, traces, and evaluations | A response or trace exposes unnecessary personal data to a user, provider, or operator. | Data minimization; tenant/customer authorization; redaction/tokenization; provider data controls. | PII scanners, access logs, leakage metrics. | Synthetic PII propagation and redaction tests. | Some necessary commerce data must be disclosed to an authorized user. |
| T-11 | Secret leakage | Credentials, tokens, and private keys | A prompt, log, document, or error includes a secret. | Secrets out of source control; secret-store boundary later; redacted logs; no secrets in retrieved content. | Secret scanners and structured-log inspection. | Repository and prompt/log scanning tests. | Operational misconfiguration can still leak secrets. |
| T-12 | Backend failure/hallucination | Trust in commerce state | Commerce API times out or fails, and the assistant claims that an action completed. | Explicit failure states; authenticated result verification; no success without authoritative result. | Backend error rate, unresolved-write queue, trace status. | Timeout-after-write and unavailable-backend tests. | External outages delay resolution. |
| T-13 | Malicious knowledge documents | Retrieval index and answer quality | An administrator uploads poisoned or oversized content that manipulates answers or exhausts resources. | Tenant-scoped ingestion; versioning; document validation/quarantine; bounded chunks; evidence thresholds. | Ingestion rejects, content flags, retrieval-quality regression. | Malicious-document and oversized-input tests. | Novel injection patterns require ongoing review. |
| T-14 | DoS/resource abuse | API, model budget, queues, and provider quotas | Repeated long prompts, audio streams, or tool loops consume resources. | Bounded input/turn/tool budgets; rate limits; cancellation; queue limits; cost monitoring. | Rate, latency, queue-depth, and cost alerts. | Load and abuse tests at target concurrency. | Traffic spikes may still degrade service. |
| T-15 | Audit tampering | Audit events and trace history | A model, user, or operator attempts to rewrite a high-risk event or hide a denied action. | Append-oriented audit design; model has no audit write authority; restricted operator access; correlation checks. | Missing sequence/correlation events and access logs. | Tamper and unauthorized-mutation tests. | Final immutability/durability depends on later storage design. |
| T-16 | Model/provider outage | Conversation continuity and safety | An LLM, speech, or retrieval provider is unavailable or returns malformed output. | Gateway abstraction; timeouts; schema validation; graceful fallback, abstention, retry, or human escalation. | Provider health, error, and fallback metrics. | Provider outage and malformed-response tests. | Feature availability falls during provider incidents. |
| T-17 | Voice transcription causes incorrect actions | Customer intent and business writes | An accent, code-switch, interruption, or partial transcript is misrecognized as confirmation or a target. | Partial transcripts cannot write; final-turn gate; typed proposal; spoken/visual summary; explicit confirmation; policy checks. | Transcript/proposal mismatch, interruption, and confirmation audit events. | Multilingual, noisy-audio, barge-in, and false-confirmation tests. | Speech recognition errors can still require repair or human help. |
